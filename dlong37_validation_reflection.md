# Validation Reflection

I reviewed Dhrumil Patel's (dpate172) ten projects across five fields, giving 50 comparisons. Before discussion, we agreed on 31 comparisons (62.0%). We resolved all 19 disagreements, reaching 100.0% agreement after discussion. CurrentStatus had the most disagreements (5 of 10), followed by HasRecovered and ActivityPattern (4 of 10 each). Of the 19 resolutions, 17 kept Dhrumil's original value, 1 kept mine and 1 was a compromise.

The final ActivityPattern labels were five declining, four irregular, and one steady. The commits just before long gaps were usually wrap-up work rather than signs of trouble: documentation fixes and a README badge in ketch_nodepy, CI and license headers in PyTransit, and News and formatting bumps in poweRlaw. Esri/geoportal-server was the clearest warning sign, since its README already marked the project as retired and its last pre-gap activity was a lone Dependabot bump. I had labelled PyTransit, cuCIM and agnwinds as cyclical based on repeated peaks. None of their series repeated at fixed intervals, so we kept Dhrumil's labels.

Recovery usually came from people already active before the gap. In PyTransit, the first post-gap commit fixed a bug reported in issue #12 during the gap. In suite2p, the return fixed issues #1144 and #1149, which had been reported before the gap. poweRlaw returned with a vignette fix and pkgdown work leading to a CRAN release, and Bo Sundman restarted opencalphad with new MQMQA modelling work. opencalphad was also the main case of an outside contributor, who added Linux build and CI work in October 2024. Both PyTransit and opencalphad were still Active at the reference date, which shows that a long gap did not mean the project had died.

Definitions also changed many conclusions reached. We agreed that any month with zero commits counts as a gap, and that any commit after it counts as recovery. This made the 1-2 month dips in suite2p, pinocchio and agnwinds count as recovered gaps, and turned Dhrumil's `Partly` for ketch_nodepy into Yes. It also changed esri to Yes, even though its only post-gap commits are README and website edits on an archived project. Recovery therefore meant resumed repository activity, not a revived project, so WhyRecovered and the comments carry that context. fhir-server and cuCIM had no empty months, so they kept N/A active project.

We resolved all five CurrentStatus disagreements by using the written September 30, 2025 reference date. I had assumed the year was a typo for 2026, and that single assumption caused every status disagreement. RecentThemes differed because Dhrumil read PR descriptions and diffs while I relied on commit messages, and his reading usually held up. We counted Dependabot commits as automated bot contributions, following the Coding Guide, and settled pinocchio as a compromise. For WhyRecovered, I had tied opencalphad's restart to earlier pre-gap work without a source saying so. We agreed to describe what resumed and claim a cause only when a commit, PR or README states one.

The categorical pre-discussion kappa values were 0.38 for HasRecovered, 0.41 for ActivityPattern, and 0.19 for CurrentStatus. N/A active project was kept as its own category, so all ten projects remained in the HasRecovered calculation. Post-discussion kappa is 1.0 because we both accepted the same final labels; it measures consensus after adjudication rather than a fresh independent assessment. WhyRecovered and RecentThemes use NA for kappa as the README requires, and resolution time is NA because we did not track it. With only ten projects per field, the results are sensitive to individual decisions. The main improvement was agreeing on written definitions, since most of our disagreements came from rules we had each assumed rather than from the commit histories.
